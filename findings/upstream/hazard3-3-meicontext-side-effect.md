# A trapping write to meicontext still modifies mie when EXTENSION_XH3IRQ = 0

## Expected behaviour

With `EXTENSION_XH3IRQ = 0` the `meicontext` CSR (0xBE5) does not exist, so
`csrrwi x0, 0xbe5, 4` raises an illegal-instruction exception. An instruction
that raises an exception must not change architectural state, so `mie` should
be unchanged afterwards. The RISC-V Sail model leaves mie at 0.

## Observed behaviour

The instruction traps with mcause = 2, and `mie` changes from 0 to 8 in the
same cycle: the `msiesave` side effect of a meicontext write (mie.MSIE set)
is applied even though the CSR is undecodable.

## Platform

CXXRTL testbench `test/sim/tb_cxxrtl`, configuration `config_nou_noxh3irq.vh`
(default with `U_MODE = 0` and `EXTENSION_XH3IRQ = 0`, attached), Hazard3
v1.1.1 (`8af99293`). The same write arm is present on `develop` (`ba0c83c6`,
`hdl/hazard3_csr.v:335`).

## Files

`config_nou_noxh3irq.vh`, `meicontext_side_effect.bin` (88 bytes, loaded at
0x80000000) and its listing `meicontext_side_effect.lst`; generated by
`mkrepro.py`, no ELF. The program prints mie, executes the write, and the trap
handler prints mcause and mie again, then exits with 1 if mie is non-zero.

## Reproduce

```
cp config_nou_noxh3irq.vh test/sim/tb_common/hdl/
cd test/sim/tb_cxxrtl && make CONFIG=nou_noxh3irq
./tb-nou_noxh3irq --bin meicontext_side_effect.bin --cycles 2000 --logfile /dev/stdout --cpuret; echo "exit $?"
```

Output on v1.1.1:

```
00000000
00000002
00000008
CPU requested halt. Exit code 1
Ran for 18 cycles
exit 1
```

## How it was found

As a counterexample from a formal equivalence check of Hazard3 against the
RISC-V Sail model. The CSR decode for meicontext is conditioned on
`EXTENSION_XH3IRQ`; the arm that applies its write side effect to mie is
conditioned only on `wen_m_mode && addr == MEICONTEXT`.
