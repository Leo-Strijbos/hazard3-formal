# Vectored mode with an unaligned mtvec BASE: entry address is BASE | 4*cause, and BASE is not legalised

## Expected behaviour

Privileged spec, mtvec: in Vectored mode "interrupts cause the pc to be set to
the address in the BASE field plus four times the interrupt cause number", and
"the MODE setting may impose additional alignment constraints on the value in
the BASE field". The RISC-V Sail model computes `base + (cause << 2)`.

Hazard3's documentation (csr.adoc, mtvec) says BASE is OR'd with the trap
offset, so the table must be aligned to its size rounded up to a power of two.
That is a legitimate implementation choice if the register enforces it: an
implementation that imposes an extra alignment constraint is expected to
legalise writes (WARL) so that mtvec never holds a BASE the constraint
excludes.

## Observed behaviour

With `MTVEC_WMASK = 0xfffffffd` (the default) every BASE bit is writable, so
`csrw mtvec, 0x80000075` stores BASE = 0x80000074 in Vectored mode and reads
back unchanged. A machine software interrupt (cause 3) then enters at
`0x80000074 | 0xc = 0x8000007c` rather than `0x80000074 + 0xc = 0x80000080`,
four bytes before the slot the ISA formula selects.

So software that sets an unaligned BASE in Vectored mode is neither rejected
(the write is not legalised) nor given ISA behaviour (the addition). Is the
intent that MTVEC_WMASK should be set by the integrator to enforce the
documented alignment, or should the core legalise it? For RP2350 the
documented alignment rule presumably keeps this out of reach of normal
software; this is reported as a conformance question rather than a functional
bug.

## Platform

CXXRTL testbench `test/sim/tb_cxxrtl`, default configuration, Hazard3 v1.1.1
(`8af99293`). Same on `develop` (`ba0c83c6`, `hdl/hazard3_csr.v:1472`).

## Files

`mtvec_vectored_unaligned.bin` (468 bytes, loaded at 0x80000000) and its listing
`mtvec_vectored_unaligned.lst`; generated by `mkrepro.py`, no ELF. The program
writes mtvec = 0x80000075, prints the read-back value, enables MSIE and MIE,
asserts the testbench's software interrupt, and waits. The word at 0x8000007c
jumps to a stub that prints 0x7c and exits 1; the word at 0x80000080 jumps to a
stub that prints 0x80 and exits 0.

## Reproduce

```
cd test/sim/tb_cxxrtl && make
./tb --bin mtvec_vectored_unaligned.bin --cycles 2000 --logfile /dev/stdout --cpuret; echo "exit $?"
```

Output on v1.1.1:

```
80000075
0000007c
CPU requested halt. Exit code 1
Ran for 28 cycles
exit 1
```

## How it was found

As a counterexample from a formal equivalence check of Hazard3 against the
RISC-V Sail model, at the interrupt-entry PC.
